    Arquitetura de IA (MarIA) e Cache Distribuído

    Bem-vindo à documentação arquitetural da MarIA (Mapeamento e Articulação de Informações Acadêmicas), a assistente inteligente do SIMCC (Sistema de Informação e Mapeamento da Competência Científica da Bahia), mantido pelo Observatório SECTI (Secretaria de Ciência, Tecnologia e Inovação da Bahia).

    Este guia apresenta em detalhes como a pipeline de inteligência artificial processa requisições de linguagem natural, realiza buscas híbridas na base científica estadual, aplica filtros de relevância semântica e utiliza uma camada distribuída de cache Redis para garantir alta performance e escalabilidade para múltiplos workers concorrentes.

    1. Visão Geral da MarIA

    A MarIA atua como uma consultora inteligente e amigável sobre o ecossistema de ciência, tecnologia e inovação da Bahia. Seu papel é traduzir dúvidas de pesquisadores, gestores públicos e cidadãos em consultas estruturadas e semânticas, sintetizando dados de currículos Lattes, artigos, livros, patentes e projetos acadêmicos.

    graph TD
    User([Usuário / Frontend]) -->|POST /ai/chat/ask ou /stream| Router[Router da MarIA]
    Router -->|1. Verifica Cache| Cache{Cache Redis}
    Cache -->|Cache Hit| ReturnCached[Retorno Imediato / Replay SSE]
    Cache -->|Cache Miss| Service[MarIAService]
    Service -->|2. Planejamento| Planner[QueryPlanner]
    Planner -->|Intenção + Filtros| Search[AISearchService]
    Search -->|3. Busca Vetorial| PG[(PostgreSQL + pgvector)]
    Search -->|4. Linha de Corte| Cutoff[QualityCutoffPolicy]
    Cutoff -->|5. Contexto Filtrado| Prompt[Prompt Builder]
    Prompt -->|6. Síntese Adaptativa| LLM[OpenAI / LLM Provider]
    LLM -->|7. Resposta / Stream| Service
    Service -->|8. Armazena Cache| Cache
    Service -->|9. Registro JSONL| Tracer[AITracer]
    Service -->|10. Resposta Final| User

    2. Pipeline Operacional de Execução

    O ciclo de vida de uma requisição de chat percorre 5 estágios principais, todos monitorados com telemetria contínua:

    Estágio 1: Recepção e Consulta ao Cache Distribuído

    1. O endpoint recebe a requisição (query, session_id, filters).
    2. O sistema gera uma chave canônica normalizada (maria:chat:ask:<hash> ou maria:chat:stream:<hash>).
    3. Em caso de Cache Hit, a resposta (ou os eventos de streaming SSE) é devolvida imediatamente (< 50ms), sem custo de tokens ou consultas ao banco de dados.
    4. Em caso de Cache Miss ou indisponibilidade do Redis, o fluxo prossegue normalmente (graceful fallback).

    Estágio 2: Planejador Semântico (QueryPlanner)

    O QueryPlanner decompõe a linguagem natural do usuário em três dimensões estruturadas: * Intenção (intent): Classifica a ação do usuário (ex: find_researcher, find_production, thematic_chat, general_question). * Consulta Semântica (semantic_query): Extrai os conceitos e termos centrais para a geração do vetor de embeddings. * Filtros Estruturados (filters): Identifica restrições relacionais explícitas (ex: instituição, gênero, área do conhecimento).

    Estágio 3: Busca Híbrida e Linha de Corte de Qualidade (Cutoff)

    A busca combina vetores de embeddings com filtros relacionais no PostgreSQL via extensão pgvector: * Similaridade Semântica: Cálculo da distância cosseno entre a pergunta e os resumos de pesquisadores e produções. * Linha de Corte (cosine_distance <= 0.65): Registros com distância cosseno superior a 0.65 (baixa correlação temática) são descartados automaticamente como ruído. * Detecção de Gaps de Base: Se nenhum registro atender ao limiar mínimo de qualidade, o sistema aciona o modo de resposta empática informando a indexação contínua da base estadual, prevenindo alucinações.

    Estágio 4: Estratégias Adaptativas de Resposta (5 Variações)

    O prompt de síntese seleciona dinamicamente uma estratégia de redação com base no volume e na diversidade dos dados:

    Variação Gatilho Comportamento da MarIA
    Modo Alto Volume Mais de 5 registros encontrados Síntese executiva panorâmica com destaques institucionais e tendências, sem listagens mecânicas.
    Modo Volume Reduzido 1 a 4 registros encontrados Análise individualizada e rica de cada registro, explicando seu alinhamento com a consulta.
    Modo Heterogêneo / Multidisciplinar Mistura de pesquisadores e produções diversas Estruturação comparativa por instituição ou tipologia de produção (artigos, patentes, etc.).
    Modo Base em Indexação 0 registros válidos após a linha de corte Mensagem acolhedora e transparente explicando que os dados do estado estão em processamento e sugerindo refinamento.
    Modo Consultoria Conceitual Dúvidas teóricas / thematic_chat Explicação didática e técnica do conceito, convidando o usuário a explorar pesquisadores no estado caso deseje.

    Estágio 5: Síntese e Streaming com Server-Sent Events (SSE)

    A resposta pode ser consumida de duas formas: * Síncrona (POST /ai/chat/ask): Retorna o payload completo com answer, intent, researchers, productions e sources. * Streaming (POST /ai/chat/ask/stream): Emite eventos SSE em tempo real nos blocos padronizados: metadata (dados estruturados e filtros), delta (pedaços do texto gerado) e done (término do stream).

    3. Camada de Cache Distribuído (Redis)

    O SIMCC foi projetado para operar com múltiplos workers Uvicorn (tipicamente entre 4 e 6 processos). Para evitar duplicidade de computação e contenção, o cache é centralizado no Redis.

    graph LR
    Worker1[Worker 1] -->|redis.asyncio| Redis[(Redis 7+)]
    Worker2[Worker 2] -->|redis.asyncio| Redis
    Worker3[Worker 3] -->|redis.asyncio| Redis
    WorkerN[Worker N] -->|redis.asyncio| Redis

    Características Técnicas do Cache:

    • Cliente Assíncrono (redis.asyncio): Pool de conexões assíncronas não-bloqueantes integrado ao ciclo de vida do FastAPI.
    • Namespaces Isolados: Chaves prefixadas por domínio (ex: simcc:ai:chat:ask:<hash>, simcc:ai:chat:stream:<hash>).
    • Replay de Streaming: O cache armazena a sequência completa de eventos SSE (metadata, deltas, done). Requisições subsequentes de stream são reemitidas com latência zero.
    • Graceful Degradation: Falhas de conexão, timeouts ou indisponibilidade temporária do Redis não interrompem a aplicação — o sistema executa o fallback silencioso para a pipeline direta.

    4. Observabilidade, Rastreabilidade e Tracing (JSONL)

    Em conformidade com a Constituição do SIMCC e os padrões de governança, todas as execuções de IA emitem eventos de telemetria estruturados no formato JSONL.

    Componentes de Telemetria:

    • AITracer: Mede a latência individual de cada estágio (planner, hybrid_search, cutoff_filtering, synthesis).
    • AIPricingEstimator: Estima tokens de entrada, tokens de saída e custo monetário associado às chamadas da OpenAI.

    5. Contratos de API e Compatibilidade com o Frontend

    Os endpoints preservam 100% de compatibilidade retroativa com os componentes do frontend visual:

    1. POST /ai/chat/ask

    Retorna o schema ChatResponse: * answer (string): Resposta formatada em Markdown com o tom adaptativo. * intent (string): Intenção classificada. * filters_extracted (objeto): Filtros relacionais identificados. * researchers (lista): Metadados dos pesquisadores relevantes. * productions (lista): Metadados das produções associadas. * sources (lista): Fontes institucionais e vínculos Lattes.

    2. POST /ai/chat/ask/stream

    Emite fluxo text/event-stream com eventos: 1. event: metadata -> Objeto SearchUIMetadata com pesquisadores, produções e filtros. 2. event: delta -> Fragmentos de texto gerados incrementalmente pelo modelo. 3. event: done -> Sinalização de término do processamento. 4. event: error -> Emissão controlada e amigável em caso de exceções.
